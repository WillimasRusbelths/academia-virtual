## Implementación y límites

- `domain/course.ts`: `withdrawCourse`, solo PUBLISHED → WITHDRAWN. No cancela
  curso ni decide cambios de sus hijos.
- `domain/group.ts`: `withdrawGroup`, cancelación terminal desde DRAFT/PUBLISHED/
  WITHDRAWN y normalización del motivo no vacío. Copias nuevas que conservan datos,
  captura y franjas; ninguna revisión o reloj se genera en el dominio.
- `application/commands.ts`: tipos/puerto `LifecycleCommand`/`LifecycleStore` y
  `LifecycleCommands`, con permiso `academic:manage`. Sin dependencia de Nest/pg.
- `infrastructure/offering-store.ts`: `createLifecycleStore`, con el escritor,
  reautorización, locks, revisiones, ledger y auditoría ya existentes. Se comparte
  descubrimiento de referencias con publicación mediante `editorialTopology`;
  no se altera el protocolo ni se añade un bucle de reintentos.
- `tests/integration/academic-offering-lifecycle.spec.ts`: 22 casos adicionales
  contra PostgreSQL real. Completan comprobaciones del escritor que las rutas
  todavía ausentes de T044 no permiten alcanzar. No reemplazan ni debilitan T044.

El descubrimiento incluye actor, asignación actual/última captura y recursos propios;
para curso, hijos PUBLISHED. Se revalida tras User → Session → Course → Group,
con UUID ordenados y redescubrimiento por rollback antes de adquirir cuentas nuevas.
Se conserva el presupuesto compartido de tres intentos y el tratamiento de COMMIT
ambiguo existente. No se bloquean grupos/cursos ajenos para comprobar agenda.

El retiro del curso escribe únicamente su estado/revisión. El de grupo cambia solo
estado/revisión; cancelarlo añade motivo normalizado y fecha, conservando el resto.
La fecha procede de `clock_timestamp()` de PostgreSQL dentro de la misma transacción,
se pasa a la regla pura y se persiste; no se admite `cancelledAt` del llamante.
La fecha no forma parte del digest porque es un hecho del servidor, no la intención.
Un replay autorizado recupera proyección actual/revisión aplicada sin cambiar fecha,
motivo ni volver a aplicar la transición. Un ID nuevo con estado inválido falla;
no se convierte en NO_CHANGE. No se exige docente habilitado para retirar/cancelar.

No se conecta a composición HTTP, no se crean rutas T049 ni interfaz T050/T051.
El cierre literal de T048 exige también T044 HTTP verde: esa dependencia sigue
abierta y no se sustituye por pruebas directas del escritor.
