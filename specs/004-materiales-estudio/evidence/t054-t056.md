## Interfaz y cliente

«Gestionar» en el listado abre la corrección de un material existente. Guarda
textos con límites Unicode de 200/2000, sin modificar archivo/grupo/autor ni
publicar implícitamente. Retiro y republicación tienen confirmación explícita y
foco de teclado; cancelar devuelve el foco al botón de origen. Preparar un archivo
nuevo es una acción separada que lleva al formulario de preparación existente.
En cancelado administrativo solo se muestra la acción de retiro y el histórico.

El controlador queda en el ámbito de grupo/cuenta, sobrevive a la recarga de
lecturas tras una escritura y se destruye al cambiar ruta/cuenta. Una denegación
borra recurso, borrador y comparación. Respuestas tardías no reconstruyen la vista.
Conflicto consulta la versión actual, conserva el borrador y exige adoptar la
revisión explícitamente antes de otra intención. Incertidumbre congela ID/payload,
consulta sin reenviar y ofrece reintento manual de la misma intención, incluso si
el primer comando ya se confirmó. No se adivina el commit por el aspecto del recurso.

El cliente añade PATCH/withdraw al registro cerrado de app y valida recibo y
recurso. Conserva mismo origen/CSRF/no-store/redirect error, errores filtrados y
aborto por sesión. El único cambio de una prueba previa es el inventario cerrado:
la sonda que rechazaba withdraw ahora rechaza replace, que sigue fuera de alcance.
Las 16 pruebas T050 originales permanecen intactas y pasan; ocho casos nuevos
comprueban rutas, opciones seguras, allowlists y respuestas malformadas.

## Carreras observadas

T055 añade 14 casos con barreras y sin sleeps de ordenación:

- Seis órdenes edit/publish/withdraw: el primero retiene el lock y el segundo se
  observa en `pg_blocking_pids`. Solo el ganador escribe; el obsoleto no deja recibo
  ni auditoría.
- Misma identidad concurrente con digest igual recupera un recibo; con textos
  distintos devuelve conflicto sin duplicar eventos.
- Reasignación confirmada mientras el comando espera se redescubre antes de
  mutación/ledger y deniega al docente anterior.
- Para cada uno de EDIT/PUBLISH/WITHDRAW, el reloj SQL aislado avanza después de
  insertar auditoría y antes de la validación final de sesión. La expiración
  revierte material, ledger y auditoría. No se altera Session mientras tiene lock.
- Una lectura binaria autorizada bloquea retiro hasta liberar su transacción.
  Las solicitudes nuevas posteriores al retiro dan 404.
- Una respuesta HTTP ya autorizada puede terminar después del retiro. Sus bytes
  siguen siendo los originales; el retiro no pretende recuperarlos.

El último ensayo inicialmente agotó su plazo: el cliente podía completar
Content-Length y reutilizar la conexión aunque `response.end` se mantuviera
retenido. Restaurar el método por sí solo tampoco resolvió la cola. El ensayo
final usa `Connection: close` en esa respuesta retenida para que la nueva solicitud
no se encole detrás de ella. No se modificó código de backend ni se relajó la
comprobación de 404, bytes o permisos. Se conservan ambos informes fallidos.

## E2E real

Seis escenarios se ejecutan en escritorio y móvil (12 casos): corrección/retiro/
republicación con teclado y descarga de alumno; sucesor con atribución propia y
autor original; histórico cancelado del administrador; conflicto con borrador
conservado; respuesta real perdida con un único efecto durable; y logout/login
con descarte de respuesta tardía de corrección. Las pérdidas y demoras interceptan
respuestas de comandos realmente ejecutados; no se sustituyen endpoints o reglas.

La fixture existente crea esquema y actores ficticios por caso, API/Vite reales
y fingerprint financiero antes/después. El focal de escritorio pasó 6/6 antes de
la ejecución completa, que incluye los 30 casos previos de US1/US2 sin cambios.

## Reproducción y registro

Usar el [entorno aislado](implementation-environment.md), sin imprimir variables
privadas ni tocar la BD manual. En el runner API:

```sh
node apps/api/scripts/database.mjs generate
npm run build --workspace @academia/api
cd apps/api
node ../../node_modules/vitest/vitest.mjs run tests/architecture src/modules/materials tests/integration/materials- --maxWorkers=2
```

Desde `apps/web`, con Chromium en el runner de navegador:

```sh
node ../../node_modules/vitest/vitest.mjs run src --maxWorkers=2
node ../../node_modules/@playwright/test/cli.js test --config playwright.materials.config.ts --reporter=json
```

Tipos API/materiales, tipos web completos y del harness, lint API/web y builds
API/web se comprueban por separado. Dos workers API y uno de navegador; cero
reintentos de navegador. La regresión ampliada histórica de 1865 casos API de
T051–T053 no se repite: producto backend íntegramente preservado, con nueva
regresión de materiales/arquitectura y carreras en este bloque.
