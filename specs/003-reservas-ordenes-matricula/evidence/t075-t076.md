## Implementación y alcance

[EnrollmentAdminController](../../../apps/api/src/modules/enrollment/entrypoints/http/admin.controller.ts) expone cinco rutas: GET orders, GET orders/:orderId, GET incidents, GET incidents/:incidentId y POST incidents/:incidentId/follow-ups bajo /api/v1/admin/enrollment. Las cuatro consultas exigen enrollment:read-all; el POST exige enrollment:incident-follow-up. GET/PUT de precio conservan enrollment:price-manage. Cada método tiene su política correcta; el catálogo completo de endpoints compilados se verifica en la prueba arquitectónica existente.

[AppModule](../../../apps/api/src/app.module.ts) y [EnrollmentModule](../../../apps/api/src/modules/enrollment/enrollment.module.ts) componen EnrollmentFollowUps con el adaptador PG real. El token vive en la aplicación; no se abre otra conexión o transacción desde el controlador. La guarda global revalida el acceso y el adaptador conserva reautorización dentro de la transacción, incluso para replay. Las consultas mantienen propiedad/proyecciones separadas y no-store.

Entradas cerradas: paginación normalizada y studentId opcional solo para lista administrativa de órdenes, UUID canónico, rechazo de query/campos desconocidos y cuerpo de seguimiento limitado a commandId/content. Autor, hora y estado económico no se aceptan como instrucciones. El POST declara HTTP200 tanto al crear como al recuperar resultado, sin 202/204 vacíos. Origin/CSRF, 16KiB, JSON estricto, mensajes cerrados y requestId siguen en el transporte existente. No se habilita ninguna ruta para resolver, devolver, trasladar, confirmar pago, matricular o cancelar financieramente.

[El módulo API de la feature](../../../apps/web/src/features/enrollment/api.ts) añade createEnrollmentAdminApi y tipos administrativos, separado del createEnrollmentApi del alumno. [La composición HTTP](../../../apps/web/src/app/http.ts) exporta enrollmentAdminApi usando el mismo cliente compartido y sus allowlists ya preparadas por ruta/método. Incluye precio, setPrice, órdenes, orden, incidencias, incidencia y followUp. Los payloads copian explícitamente solo campos aprobados; no se envían por spread campos de autoridad, resolución o evidencia. Las rutas propias mantienen su contrato y rechazan un DTO administrativo enriquecido.

El cliente verifica estructuras cerradas, IDs del recurso/comando/incidencia, revisión exacta, timestamps UTC con seis fracciones, coherencia del recibo y contenido inmutable del seguimiento. Distingue precio ausente de cero y conserva importes superiores a Number.MAX_SAFE_INTEGER como cadenas. Las incidencias pueden reflejar importe negativo/moneda incompatible sin convertirse en pago aplicado. Se rechazan claves privadas, resolución inventada, duplicados y notas de otra incidencia. El replay de precio puede devolver una proyección actual más reciente que el recibo original, sin interpretar esa diferencia como otro efecto. No hay polling, almacenamiento local o reenvío automático; logout cancela y descarta respuestas tardías.
